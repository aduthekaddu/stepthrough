<Segment id="s02-setup-first" goal="The engine sets up every declared name before the first line runs">

That result raises a fair question. If a script runs from top to bottom, one line after another, how could line 1 know anything about a name that is only written on line 2?

Before looking for the reason, try the same thing with a function. This script calls a function on its first line and only creates it below.

    { id: "c", text: "TypeError: double is not a function", misconception: "HOIST-FN-AS-VAR", feedback: "You expected double to exist but hold undefined, the way a var does. A function declaration starts with its function already in place. Segment 8 lists the starting state of each kind." }
  ]}
  explain="Before any line runs, the engine creates a binding for every declaration. A function declaration's binding already holds the function."
/>

The call printed `8`. So the engine (the program that runs JavaScript, such as V8 inside Node and Chrome) does not start by running line 1. First it reads the whole script and finds every piece of code that creates a name. Such a piece of code is called a <Term id="declaration">declaration</Term>. The kinds are `var`, `let`, `const`, `function` and `class` declarations, and the parameters of a function.

For each declaration, the engine creates a binding (from lesson 1.1: a name paired with a value) before any line runs. Running code is therefore two steps: first set up all the names, then run the lines in order.

For a `function` declaration, the binding already holds the function at the end of the first step. That is why line 1 could call it. You can check this without calling it:

<Code runnable code={`console.log(typeof double); // → function
function double(n) {
  return n * 2;
}`} />

Other kinds of declaration start in other states, which is what the hook showed. The next segment shows where these bindings are kept.

</Segment>

<Segment id="s03-records" goal="Names live in a table of bindings called an environment record">

The engine keeps bindings in tables. Each table connects names to their current values. The ECMAScript specification (the document that defines JavaScript, often called "the spec") calls such a table an <Term id="environment-record">environment record</Term>.

Read the picture before you step through it. The box is one environment record, and each row is one binding. The label at the start of a row is the kind of declaration that made it: `var`, `let`, `const`, `function` or `param`. Next comes the name, then the current value. A row can also say that it has no value yet. That means the binding exists but has not been given any value; the spec word is "uninitialized".

Look at the first step before you press next. All four rows exist before line 1 has run, in three different states.

<Viz example="global-setup" view="scope" gate="call-early" pauseAt={[1]} title="The global record before and during the run" />

Watch what each step changed. Running a line changed the value in a row that already existed. It never added a row.

You might ask: "Is this table a real thing in memory?" The spec says environment records are a description. A real engine may store variables any way it likes, as long as every program behaves exactly as if these tables existed. So the tables are a model that predicts behaviour exactly. They are not a map of memory.

<Sidenote>The spec says: "Environment Records are purely specification mechanisms and need not correspond to any specific artefact of an ECMAScript implementation." ([ECMAScript 9.1](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-environment-records))</Sidenote>

</Segment>

So calling a function is a jump with a promise to come back. The engine must remember where the caller stopped, run the function, and then return to that exact place. The function also needs its own names.

For each piece of code that is running, the engine keeps a small record: which function it is (or none, for the script itself), how far it has got, and which environment records it uses to find names. This is called an <Term id="execution-context">execution context</Term>. The spec names its main parts `Function`, `LexicalEnvironment` (where name lookups start) and `VariableEnvironment` (where `var` bindings go). The sidenote below has the full list.

Running a script creates the first execution context. Calling a function creates a new execution context and also a brand new environment record for that one call. This record is a <Term id="function-environment">function environment record</Term>. It holds the call's parameters and the names declared at the top level of the function body. The new context goes on top of the stack. Step through and watch the second context appear.

<Viz example="first-call" view="scope" pauseAt={[2]} title="Calling greet" />

The stack of execution contexts is the call stack from lesson 0.1 (the list of function calls that have started and not finished, newest on top). The spec calls it the execution context stack. The running context is always the one on top.

Is an execution context the same as a stack frame from lesson 0.1? A stack frame was the general idea of one entry per call. In JavaScript, the spec calls each entry an execution context, and each engine decides how to lay it out in memory.

When `greet` returned, its context left the stack, and nothing referred to its record any more. Lesson 1.3 shows when a record lives on after its call has ended.

<Sidenote>Spec fields: code evaluation state, Function, Realm (the built-ins, such as `Array`, and the global record), ScriptOrModule, LexicalEnvironment and VariableEnvironment. "It is impossible for ECMAScript code to directly access or observe an execution context." ([ECMAScript 9.4](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-execution-contexts)). The pictures draw one record per call; the spec sometimes splits it in two (lesson 1.3), with the same lookup results here.</Sidenote>

</Segment>

<Segment id="s06-lookup" goal="A lookup walks outer references until it finds the name or runs out of records">

In the `greet` example, `greeting` was not in `greet`'s record, but the engine still found it. How?

Every environment record has a link to the record around it, called its <Term id="outer-reference">outer reference</Term> (the spec field is `[[OuterEnv]]`). The global record is the outermost one, so its outer reference is `null`, meaning nothing.

A lookup checks the current record first. If the name is not there, it follows the outer reference and checks that record. It stops at the first record that has the name.

The chain of records a lookup walks has a teaching name: the <Term id="scope-chain">scope chain</Term>. The spec does not use this term. "Scope" here means the part of the code where a name can be used; lesson 1.3 goes deeper. So what happens when the chain runs out?

You might ask: "Why does `full`'s record point to `page`, and not to whoever called `full`?" The outer reference comes from where the function was written, not from who calls it. Lesson 1.3 is about exactly this.

<Segment id="s07-global" goal="The global record has two parts, and only var and function land on the global object">

The outermost record is different from the others. Its name is the <Term id="global-environment">global environment record</Term>, and it has two parts.

One part is backed by a real object that your code can touch, the <Term id="global-object">global object</Term>. Every host names it `globalThis`, and browsers also call it `window`. At the top level of a script, `var` and `function` declarations become properties of this object.

The other part is a plain table, like the records you have seen so far. It holds top-level `let`, `const` and `class` bindings, which are not properties of the global object.

Only var and function declarations go there. let, const and class go into the global record's other part, which has no properties, so globalThis.b is undefined." },
    { id: "c", text: "undefined undefined undefined", misconception: "GLOBAL-NOTHING-ON-OBJECT", feedback: "That is how ES modules and Node CommonJS files behave, so this belief is reasonable if you mostly write modules.   ]}
  explain="The global environment record has an object part, which is the global object, for var and function, and a declarative part for let, const and class."

The output is `1 undefined function`. `a` and `f` are properties of the global object. `b` lives only in the table part of the global environment record.

You might ask: "Why keep two kinds of global names?" Before ES2015 (the 2015 edition of JavaScript), every global declaration created a property on the global object. The new `let`, `const` and `class` needed a state with no value yet, and an object property has no way to be marked "not yet initialized". So `var` and `function` stayed on the object, so that old code kept working, and the new kinds got their own table. Segment 13 gives the source.

In a module (a file that uses `import` and `export`, or a Node CommonJS file), top-level declarations belong to the module and never touch `globalThis`. Most code you write in Next.js and Node is modules. The snippets in these lessons run as classic scripts, like a browser `<script>` tag.

<Sidenote>Measured in Node 26: as a classic script, `var x = 1; console.log(globalThis.x)` prints 1. Inside an ES module it prints undefined. MDN: in "Node.js CommonJS modules and native ECMAScript modules, top-level variable declarations are scoped to the module." ([MDN var](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/var))</Sidenote>

A top-level `let` is still a global name. Every part of the script can read it. It is just not a property of the global object:

<Code runnable code={`let b = 2;
console.log(b, globalThis.b, "b" in globalThis); // → 2 undefined false`} />

</Segment>

<Segment id="s08-instantiation" goal="Declaration instantiation gives each declaration kind its own starting state">

The setup step has a real name. The spec calls it GlobalDeclarationInstantiation for a script and FunctionDeclarationInstantiation for a function call. This lesson calls both <Term id="declaration-instantiation">declaration instantiation</Term>. It runs after the new execution context is on the stack and before the first statement.

Many tutorials call it the "creation phase", and call the second step, running the statements in order, the "execution phase". Both are teaching names, not spec terms.

Here is what declaration instantiation leaves in each binding, and what the declaration's own line does later, when execution reaches it:

- **Function declaration.** Holds a new function object (functions are objects, lesson 1.1). Its line does nothing.
- **`var x`.** Holds `undefined`. `var x = 5;` assigns 5. `var x;` does nothing.
- **`let x`.** Exists with no value. `let x = 5;` gives it its first value. `let x;` gives it `undefined`.
- **`const x`.** Exists with no value. `const x = 5;` gives it its one and only value.
- **`class C`.** Exists with no value. Its line creates the class and gives it to `C`.
- **Parameter.** Holds the argument passed in, filled left to right. A parameter has no line of its own.

Declaration instantiation reads every declaration in the body, even ones after a `return` or inside an `if` that never runs.

<Segment id="s09-hoisting" goal="Hoisting is a teaching name for the effects of declaration instantiation; no code moves">

There is a word everybody uses for these effects: <Term id="hoisting">hoisting</Term>. MDN says it "refers to the process whereby the interpreter appears to move the declaration of functions, variables, classes, or imports to the top of their scope, prior to execution of the code." Notice the word "appears". Hoisting is a teaching name. The spec never uses it.

MDN lists four behaviours that people call hoisting. A function can be called before its line. A `var` can be read before its line, and gives `undefined`. A `let`, `const` or `class` changes what a name means even above its line. An `import` takes effect before the rest of the code runs. All four are effects of declaration instantiation.

You might ask: "Then why does everyone say declarations move to the top?" Picturing the declaration lifted to the top predicts the `var` and function cases well. But it predicts `undefined` for `let`, which is wrong, and it hides the fact that there are two separate moments. Now replay the hook with the visualizer.

<Viz example="hook-replay" view="scope" gate="hook" pauseAt={[1]} title="The hook, replayed" />

Here is the first hook line, exactly. The `price` binding existed from declaration instantiation, holding `undefined`. Line 1 printed that value. For a `var`, line 2 is only an assignment, and it put 100 into the binding.

`total` also existed in the record, yet reading it threw. The next segment explains the state `total` was in. No code moved at any point.

</Segment>

<Segment id="s10-tdz" goal="A let or const binding exists before its line but has no value, and touching it throws">

Declaration instantiation creates `let`, `const` and `class` bindings but leaves them with no value. From that moment until the declaration's line runs, the binding is in the <Term id="tdz">temporal dead zone</Term>, or TDZ.

During the TDZ, any read of the name, or any assignment to it, throws a `ReferenceError`. Node words it as `Cannot access 'total' before initialization`.

The binding is still real, and lookups find it. That matters when an outer record has a binding with the same name, because a lookup checks the current record before it follows the outer reference.

Calling `check` ran declaration instantiation for that call, and it created `check`'s own `level` binding with no value. The lookup for `level` on line 3 checked `check`'s record first, found that binding in its TDZ, and stopped there. It never reached the global `level`, so `"outer"` was never possible.

The trace engine words the error differently from Node. The error type is the same; only the message text belongs to each engine.

Blocks, the code between `{` and `}`, get their own records for `let` and `const` too. Lesson 1.3 covers block records. The runnable example below throws for the same reason.

<Sidenote>"If the binding exists but is uninitialized a ReferenceError is thrown, regardless of the value of strict." ([ECMAScript GetBindingValue](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-declarative-environment-records-getbindingvalue-n-s)). "Temporal dead zone" is the name MDN and the language designers use; the spec itself only says "uninitialized".</Sidenote>

</Segment>

<Segment id="s11-typeof" goal="typeof is safe only for names that do not exist at all">

In segment 6, `typeof` did not throw for a name that does not exist anywhere on the scope chain. It gave back `"undefined"`. Does it also protect you from a binding that exists but is in its TDZ?

<Predict
  id="tdz-typeof"
  prompt="ghost is never declared. What does this print?"
  code={`console.log(typeof ghost);
console.log(typeof later);
let later = 1;`}
  answer="b"
  options={[
    { id: "a", text: "undefined\nundefined", misconception: "TDZ-TYPEOF-SAFE", feedback: "You trusted typeof to never throw. It only has a special case for names that cannot be found. later can be found, and reading it in its dead zone throws." },
    { id: "b", text: "undefined\nReferenceError: Cannot access 'later' before initialization", feedback: "Right. ghost cannot be found, so typeof returns \"undefined\". later is found and is uninitialized, so reading it throws." },
    { id: "c", text: "ReferenceError: ghost is not defined", misconception: "TYPEOF-UNDECLARED-THROWS", feedback: "You expected typeof to throw for an unknown name, like a plain read. typeof returns \"undefined\" when the lookup finds nothing." }
  ]}
  explain={"typeof first asks whether the name resolves. If not, it returns \"undefined\". If it does, it reads the value, and an uninitialized binding throws."}
/>

The first line printed `undefined`, and the second threw a `ReferenceError`. The reason is the order of steps inside `typeof`.

First, `typeof` asks whether the name can be found on the scope chain at all. `ghost` cannot be found, so `typeof` stops and returns `"undefined"`.

If the name can be found, `typeof` reads its value. `later` is found, and it is in its TDZ, so the read throws.

So a check like `typeof x === "undefined"` is safe only for a name that may not exist at all, such as a global that some browsers do not have.

<Segment id="s13-why-tdz" goal="The TDZ was chosen so one name means one binding and a const is never seen with two values">

You might ask: "Would it not be simpler to give `let` the value `undefined`, like `var`?"

The designers of JavaScript asked the same question. When `let` and `const` were being designed (they arrived in ES2015), TC39, the committee that designs JavaScript, discussed what should happen when a name is used above its declaration in the same block. In 2008, Waldemar Horwat listed four options:

1. It is an error if the use is written above the declaration ("lexical dead zone").
2. The use refers to an outer variable with the same name if it is written above ("lexical window").
3. It is an error if the use runs before the declaration ("temporal dead zone").
4. The use refers to the outer variable if it runs before ("temporal window").

Options 2 and 4 let one name mean different variables at different places, or at different times, inside one block. Option 1 would forbid functions that call each other, because one of them must be written first. Option 3 allows that, as long as the calls run after both lines:

<Code runnable code={`const isEven = (n) => (n === 0 ? true : isOdd(n - 1));
const isOdd = (n) => (n === 0 ? false : isEven(n - 1));
console.log(isEven(4)); // → true`} />

After nearly two years of discussion, the committee chose option 3, the temporal dead zone. One rule came with it: inside one scope, a name has exactly one binding.

One more consequence follows from this choice. A `const` is meant to have one value forever. If a `const` started as `undefined`, like a `var`, code could read it before and after its line and see two different values. With the TDZ, any read before the line throws, so a `const` is only ever seen with its one value. The same rule turns a quiet bug, reading `undefined` too early, into an error on the exact line.

The TDZ also explains segment 7. An object property cannot be "not yet initialized", so top-level `let` and `const` could not live on the global object.

<ExplainBack
  id="why-tdz"
  prompt="In two sentences: why does a const need a dead zone when a var does not?"
  rubric={[
    "A const binding exists from declaration instantiation but gets its one value only when its line runs",
    "If it started as undefined, code could read it before and after its line and see two different values",
    "The dead zone makes any read before the line throw, so a const is only ever seen with its one value",
    "var has no such promise; it is allowed to change, so starting as undefined breaks nothing"
  ]}
/>

<Sidenote>Source: Allen Wirfs-Brock and Brendan Eich, "JavaScript: The First 20 Years", Proc. ACM Program. Lang. 4, HOPL (2020), pages 111 to 113 ([doi.org/10.1145/3386327](https://doi.org/10.1145/3386327)).</Sidenote>

  explain={"In pair(1), a gets 1 and its default never runs. In pair(), a's default b runs while b is still uninitialized, which is a dead zone too: ReferenceError: Cannot access 'b' before initialization."}
/>

</Segment>

<Segment id="s18-in-the-wild" goal="Where execution contexts and the TDZ show up in React, Zod, Express and Java">

**React and Next.js.** A component near the top of a file can use a `const` style object or helper declared lower in the same file. It works because React calls the component later, when it renders, and by then the whole module has run. Time matters, not position. Code at module level that runs right away and reads a `const` declared below it throws the TDZ error instead. You will also meet the same message, `Cannot access 'X' before initialization`, when two modules import each other in a circle; lesson 1.10 (modules) explains that case.

<Code runnable code={`function Badge() {
  return { type: "span", props: { style: badgeStyle } };
}
const badgeStyle = { color: "teal" };
console.log(Badge().props.style.color); // → teal`} />

**Zod in DevSecret.** If one schema uses another schema that is declared below it, the file throws as soon as it loads, because `z.object({...})` reads its argument right away. Zod's documentation says, for a schema that refers to itself or to a later schema: "use a getter on the key. This lets JavaScript resolve the cyclical schema at runtime." A getter is a property written as a function that runs each time the property is read. So the lookup of the other schema happens later, after its `const` line has run. In the runnable version below, `object` stands in for `z.object`.

<Code runnable code={`const object = (shape) => ({ shape });
const Project = object({
  get secrets() {
    return Secret;
  },
});
const Secret = object({ key: "string" });
console.log(Project.shape.secrets === Secret); // → true`} />

**Express.** Route handlers are often registered at the top of a file and call helpers written at the bottom. That works for two reasons from this lesson: function declarations exist from declaration instantiation, and the handlers only run later, when requests arrive, so even `const` arrow helpers have their values by then. Below, a tiny `app` object stands in for Express.

<Code runnable code={`const routes = [];
const app = { get: (path, handler) => routes.push({ path, handler }) };
app.get("/health", (req) => reply(req.path));
function reply(path) {
  return "ok " + path;
}
console.log(routes[0].handler({ path: "/health" })); // → ok /health`} />

**Java, for contrast.** Java checks reads of unassigned locals when the code compiles. The Java Language Specification says every local variable must be "definitely assigned" before its value is read, or the program does not compile (JLS 16). A Java local's scope also starts at its own declaration (JLS 6.3). So if a method reads `level` above `String level = ...;` and the class has a field named `level`, the read means the field. That is option 2, the "lexical window" that JavaScript's designers rejected. Java methods, on the other hand, are visible in the whole class body, much like function declarations in a JavaScript script. JavaScript does its checks at run time, with the TDZ.

</Segment>

<InterviewQ

  rubric={[
