<Segment id="s02-values" goal="Everything a program works with is a value, and the spec puts every value in one of eight types: seven primitive types and Object">

## Eight kinds of data

Take any single piece of data a program works with: `42`, `"hi"`, `true`, or a whole `{ name: "Asha" }`. Each one is called a <Term id="value">value</Term>. The ECMAScript specification (we will call it the spec from now on) calls it an "ECMAScript language value". Everything the engine, the program that runs JavaScript, computes with is a value.

The spec puts every value into exactly one of eight types. Seven of them are Undefined, Null, Boolean, Number, BigInt, String and Symbol. (Type names are written with a capital letter, like Number; the values themselves appear in code, like `42`.) A value of one of these seven types is called a <Term id="primitive">primitive</Term>.

The eighth kind is different. It is a container that holds a collection of properties, each one a name with something stored under it. A value of this kind is called an <Term id="object">object</Term>, and the spec names its type Object. The rule is short: any value that is not an object is a primitive.

Why split the world in two? Because the two kinds behave differently when you copy them, change them and compare them. That difference is what this whole lesson is about.

<Code runnable code={`console.log(undefined, null, true, 42, 10n, "hi", Symbol("id"));
console.log({ name: "Asha" }, [1, 2], function greet() {});`} />

<Sidenote>Spec 6.1: "The ECMAScript language types are Undefined, Null, Boolean, String, Symbol, Number, BigInt, and Object." And: "An ECMAScript language value that is not an Object is a primitive value." [tc39.es/ecma262, 6.1](https://tc39.es/ecma262/#sec-ecmascript-language-types)</Sidenote>

Two of these types may be new to you. A bigint, written with an `n` at the end (`10n`), is a whole number of any size. A symbol, made by `Symbol("id")`, is a unique token, mostly used as a property name that cannot clash with any other; the text in brackets is only a label.

<Code runnable code={`console.log(2 ** 64, 2n ** 64n); // → 18446744073709552000 18446744073709551616n`} />

A Number is a 64-bit floating-point value, like Java's `double`, so very large whole numbers lose their last digits. A bigint keeps every digit.

The first line of the earlier box printed one primitive of each of the seven types. `undefined` is what `let x;` gives `x` when no value is written, and what reading a missing property gives. `null` is the value you write on purpose to say "no object here"; the spec describes it as "the intentional absence of any object value".

The second line prints three objects. You may ask: arrays and functions feel like their own types, are they not? No. The spec has no Array type and no Function type. An array is an object with numbered properties and a `length`. A function is an object that can also be called; the spec says "All functions in ECMAScript are members of the Object type."

</Segment>

When code runs, you often need to ask "what kind of value is this?". JavaScript has an operator for that. You write it before a value, and it returns a string that names the value's type. This operator is called <Term id="typeof">typeof</Term>. Predict what it says for these three values.

  explain="typeof follows a fixed table in the spec: null gives object, callable objects give function, and every other object gives object."

The spec gives `typeof` a fixed table. `undefined` gives `"undefined"`, a boolean `"boolean"`, a number `"number"`, a bigint `"bigint"`, a string `"string"` and a symbol `"symbol"`. Then come the two oddities.

First, `null` gives `"object"`, even though `null` is a primitive. You may ask: if `null` is not an object, why does `typeof` say it is? MDN tells the history. In the first implementation of JavaScript, a value was stored as a type tag (a small number saying what kind of value it is) plus the data. The tag for objects was `0`. `null` was stored as the null pointer, memory address zero (`0x00` on most machines), so it carried the object tag. A fix that would make `typeof null` return `"null"` was proposed for the language and rejected. So the old result stayed. The spec still lists `null` as a primitive.

Second, functions give `"function"`. They are objects, but the spec checks for one extra ability, an internal method called `[[Call]]`, and reports objects that have it as `"function"`. (The spec writes an object's hidden internal parts in double brackets; your code cannot read them directly.) Every other object, arrays included, gives `"object"`. To test for an array, use `Array.isArray(value)`.

One more useful fact: `typeof` on a name that was never declared returns `"undefined"` instead of throwing an error. A `let` or `const` name read before its line runs is a different case: that throws, and lesson 1.2 explains why.

Here is the whole table in one run. A class is a function too (lesson 1.5), so it also gives `"function"`.

<Code runnable code={`console.log(typeof undefined, typeof true, typeof 42, typeof 10n, typeof "hi", typeof Symbol("id"), typeof null); // → undefined boolean number bigint string symbol object
console.log(typeof {}, typeof [], typeof function () {}, typeof class {}); // → object object function function`} />

<Sidenote>Spec 13.5.3.1: "If value is null, return "object"." and "If value has a [[Call]] internal method, return "function"." Browsers add one more case: the old `document.all` object gives `"undefined"`. [typeof in the spec](https://tc39.es/ecma262/#sec-typeof-operator), [MDN on typeof null](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/typeof#typeof_null)</Sidenote>

<Segment id="s04-bindings" goal="A binding is a name that holds a value; let b = a gives b the value a has now, and nothing links the two names afterwards">

## Names hold values

A program needs a way to give a value a name, so it can use the value again later. The pair of a name and the value it holds right now is called a <Term id="binding">binding</Term>. In everyday speech, "variable" means the same thing. `let a = 5;` creates a binding: the name `a`, holding `5`. In the spec, bindings live inside a structure called an Environment Record; lesson 1.2 is about that structure.

Dan Abramov's course Just JavaScript draws a variable as a "wire" from the name to a value. He says himself that "A 'wire' is not a JavaScript concept"; it is a picture to think with. This lesson draws the same idea as rows in a box, and the diagram below is the first one you will step through. Its parts:

- The box labelled **Global** lists the names declared at the top level of this script, one row per name.
- A primitive is written inside its row.
- Before its line runs, a `let` name already has a row but holds nothing at all, not even `undefined`; reading it then would throw an error. The diagram shows this as "uninitialized". Lesson 1.2 explains why.

The diagram stops before `a = 6` and asks what changes next. Decide before you step.

<Viz example="values-primitive-copy" view="memory" pauseAt={[3]} title="Copying a primitive" />

`let b = a` read the value of `a` at that moment, `5`, and gave `b` that value. Then `a = 6` changed only the row for `a`.

You may ask: doesn't `b = a` tie `b` to `a`, like a formula in a spreadsheet cell? No. `=` reads the right side once, when the line runs, and stores the result. Nothing remembers where the value came from.

Why are primitives drawn inside the row? It is a drawing choice that keeps the picture small. It is not a claim about where an engine keeps the `5` in memory, the computer's working storage. Segment 11 comes back to this.

</Segment>

<Segment id="s05-immutable" goal="A primitive value can never be changed; code that seems to change one makes a new value and gives a binding that new value">

## Values that never change

Can you change the number `5` itself, so that every `5` in the program becomes something else? Of course not. The same is true of every primitive. A value that cannot be changed after it is made is called <Term id="immutable">immutable</Term>, and every primitive value is immutable. Run this code, which tries to change a string and a number.

<Code runnable code={`let word = "cat";
word[0] = "b";
console.log(word); // → cat
console.log(word.toUpperCase()); // → CAT
console.log(word); // → cat
let count = 1;
count = count + 1;
console.log(count); // → 2`} />

`word[0] = "b"` did nothing. A string cannot be changed, so the write is thrown away. It fails silently because every example in this lesson runs in sloppy mode, the old default rules for a plain script. Strict mode is a stricter set of rules that you turn on with `"use strict"` (modules and class bodies are always strict). There the same line throws `TypeError: Cannot assign to read only property '0' of string 'cat'`; TypeError is one of JavaScript's built-in error types, like a Java exception class.

`word.toUpperCase()` did not change `word` either. It built a new string, `"CAT"`, and returned it. No string method changes the original string. But how can a primitive have a method at all? When you read a property of a string, JavaScript wraps the string, for that one moment, in a temporary String object that has the methods. MDN calls it a wrapper object. The wrapper is thrown away afterwards; the string inside never changes.

You may say: but `count = count + 1` clearly changes `count`! It changes which value the binding holds. The number `1` itself never changed. The right side computed a new number, `2`, and `=` gave the binding that new value. Changing a binding and changing a value are two different things, and keeping them apart is the key to the rest of this lesson.

<Sidenote>MDN: "All types except Object define immutable values" and "JavaScript strings are immutable." [MDN, JavaScript data types](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Data_structures)</Sidenote>

</Segment>

The diagram below has two new parts. An object is drawn as its own box on the right, outside the Global box. A row that holds an object does not contain it; the row holds an arrow to the box.

<Viz example="values-alias" view="memory" gate="alias" pauseAt={[3]} title="Two names, one object" />

That arrow is the heart of this lesson. In the spec, assigning or passing an object never makes a new object: the very same object is what arrives. What travels between names is a way to reach that one object. This way to reach an object is called a <Term id="reference">reference</Term>, and the diagram draws it as an arrow. The arrow pictures behaviour, not memory layout.

Now the steps make sense. The object literal `{ n: 1 }`, an object written directly in code, made one object. `let b = a` gave `b` the value of `a`, exactly as with `5` in segment 4, but this value is an object, so `b` now holds a reference to the same object. Two arrows, one object. `b.n = 2` followed the arrow in `b` and changed the object at its end, which is the same object `a` reaches.

You may ask: so does `let b = a` copy the object or not? It does not. `=` never copies an object; only the reference is copied.

<Sidenote>Spec 5.2.8: references to objects "must be explicitly passed from one place to another". The spec's "Reference Record" ([6.2.5](https://tc39.es/ecma262/#sec-reference-record-specification-type)) is a different idea.</Sidenote>

</Segment>

<Segment id="s07-identity" goal="Every object has its own identity, so two objects with equal contents are still two objects, while primitives have no identity">

## Same contents, different objects

Two object boxes can hold the same data and still be two boxes. Each object carries a hidden mark that no other object has, and that mark never changes; it is not a property, so you cannot read it. The spec calls it <Term id="identity">identity</Term>. For objects, `===` asks one question: are both sides the same object? Run this and compare.

<Code runnable code={`const a = { n: 1 };
const b = { n: 1 };
const c = a;
console.log(a === b); // → false
console.log(a === c); // → true
console.log("hi" === "hi"); // → true
console.log(Symbol("id") === Symbol("id")); // → false`} />

`a` and `b` are two objects with equal contents, so `false`. `a` and `c` hold references to one object, so `true`.

Most primitives have no identity. Two numbers are equal when they are the same number (segment 12 shows two special cases), so one `5` is as good as any other `5`, and two `"hi"` strings are equal because they have the same characters. The spec lists the values without identity: `undefined`, `null`, booleans, numbers, bigints and strings. Symbols are the one primitive with identity: each symbol is unique, although it can never be changed. (The exception is `Symbol.for("key")`, which returns one shared symbol per key.) That is why each call to `Symbol("id")` gives a new, different symbol.

You may ask: if `a` and `b` look exactly alike, in what way are they different? Set `a.n = 5` and look at `b.n`: it is still `1`. Two identities mean two separate things that can change apart.

Coming from Java: for objects, `===` works like Java's `==`, which is true only when "both refer to the same object". Strings are different. In Java, two distinct `String` objects with the same text are not `==`, and you need `s.equals(t)`. In JavaScript, `===` on strings already compares the text.

<Sidenote>Spec 5.2.8: "each value with identity is unique and therefore only equal to itself." [Identity](https://tc39.es/ecma262/#sec-identity). Java: [JLS 15.21.3](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.21.3).</Sidenote>

</Segment>

## Changing an object versus moving a name

  explain="A bare name on the left of = moves that name's arrow. A property on the left, like b.n, changes the object at the end of the arrow."

The diagram below runs a longer script that does both kinds of `=` in turn: `b.n = 2` as in segment 6, then `b = { n: 3 }`, then `b.n = 4`.

<Viz example="values-reassign" view="memory" gate="reassign" pauseAt={[4]} title="Changing an object, then moving a name" />

When the left side of `=` is a property, like `b.n`, JavaScript follows the arrow in `b` and changes the object at its end, in place. Setting a property, deleting one (`delete b.n`), or pushing to an array (`list.push(x)`) all work this way. This is called <Term id="mutation">mutation</Term>. The object itself changed, so every binding with an arrow to it sees the change. That is why `a.n` became `2` in segment 6.

When the left side is a bare name, like `b`, only the row for `b` changes: its arrow now points at a different object. No object changed. This is called reassignment. The question above had only a reassignment, no `b.n = 2`, so `a.n` stayed `1`.

You may ask: both lines use `=`, so why do they do different things? Because the left side decides where the value goes. The spec first evaluates the left side to find the place to store into (a binding, or a property of some object), then evaluates the right side, then stores that value in the place.

<Sidenote>Spec 13.15.2, simple assignment: evaluate the left side to a Reference Record (the spec's internal record of where to store, not our arrow), evaluate the right side to a value, then `PutValue` stores it. [Assignment](https://tc39.es/ecma262/#sec-assignment-operators-runtime-semantics-evaluation)</Sidenote>

</Segment>

`const` creates an immutable binding. In the diagrams' terms, it locks the arrow in the `settings` row. Reassigning `settings` would move that arrow, so JavaScript throws a `TypeError` (Node, the runtime you use outside the browser, says "Assignment to constant variable."). The object at the end of the arrow was never protected, so `settings.theme = "dark"` worked. MDN puts it in one line: `const` creates "immutable bindings, not immutable values".

<Sidenote>In spec terms, `const` creates its binding with the operation CreateImmutableBinding, and the operation SetMutableBinding throws a TypeError for an immutable binding. [Spec 9.1.1.1.5](https://tc39.es/ecma262/#sec-declarative-environment-records-setmutablebinding-n-v-s), [MDN const](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/const)</Sidenote>

If you want an object whose properties cannot change, `Object.freeze` does that. It is shallow: it freezes one object's own properties, not the objects they refer to. It also cannot stop a Map or a Set from changing its entries, because entries are not properties.

<Code runnable code={`const config = Object.freeze({ port: 3000, db: { host: "localhost" } });
config.port = 9999;
config.db.host = "prod";
console.log(config.port); // → 3000
console.log(config.db.host); // → prod`} />

The write to `port` was ignored, because this runs in sloppy mode; in strict mode it would throw and stop the script. The write to `db.host` went through, because `db` points to a second object that nobody froze.

You may ask: then what is `const` good for? It tells every reader that this name points to the same object for its whole life. That rules out a whole class of bugs where some line far away points the name somewhere else.

</Segment>

## Back to the puzzle: passing an object

Now you have every piece you need for the opening puzzle. When a function is called, the spec first works out the value of each argument. Then each parameter becomes a new binding that holds one of those values. For a plain parameter like `user`, that works just like `=`.

The diagram adds one part. During the call, a second box appears with the call's own names. It belongs to the call's stack frame, the record a function call gets while it runs. When the call ends, its frame leaves the stack and the box disappears. (Lesson 1.3 shows functions that keep a finished call's names reachable.) Any object that nothing points to any more is dropped from the picture; the garbage collector, the part of the engine that frees memory nothing can reach, may reclaim it later. The diagram runs the puzzle code with one extra line, `return user.name;`, to give a step right after the reassignment. Watch which arrow moves.

<Viz example="values-pass-object" view="memory" gate="hook" pauseAt={[4, 5]} title="Passing an object to a function" />

<ExplainBack
  id="e1-hook"
  prompt="In one or two sentences: why did player.name become Riya and not Kabir?"
  rubric={[
    "The parameter user starts with a copy of player's reference, so both reach the same object.",

Calling `rename(player)` copied the value of `player`, a reference, into the new binding `user`. Two arrows, one object. `user.name = "Riya"` is a mutation, so it changed the shared object. `user = { name: "Kabir" }` is a reassignment, so it moved only the arrow in the call's box. When the call ended, that box went away, and `player` still pointed to the original object, now named `"Riya"`.

You may ask: isn't this pass-by-reference, then? No. In true pass-by-reference, as with C++ reference parameters, `user` would be another name for the variable `player` itself. Then `user = { name: "Kabir" }` would move `player` too, and the output would be `Kabir`. JavaScript always passes the value. An object is never copied on the way in: the parameter gets its own copy of the reference, so it reaches the same object.

For objects, Java works exactly the same way (strings differ: Java strings are objects, JavaScript strings are primitives). The Java tutorial says reference parameters "are also passed into methods by value", so "the passed-in reference still references the same object as before", while "the values of the object's fields can be changed in the method". Same rule, same diagram.

<Segment id="s11-engine-detail" goal="The spec never says where values are stored; primitives on the stack and objects on the heap describes some engines and the JVM, not JavaScript">

## Where values live: the spec is silent

Many tutorials and Java courses teach a rule of thumb: primitives live on the stack (the call stack of frames from lesson 0.1), and objects live on the heap, the large memory region where data is allocated while the program runs. Check that rule against the spec.

## The full rule behind `===`

Now the whole rule. `===` compares two values and never converts either one to another type. This comparison is called <Term id="strict-equality">strict equality</Term>. Predict all four results.

<Predict
  id="strict"

  options={[
    { id: "a", text: "false true true false", feedback: "Right. 0 / 0 is NaN, which is never ===; the two zeros are equal under ===; strings compare by characters; two arrays are two objects." },
    { id: "b", text: "true true true false", misconception: "NUM-NAN-SELF-EQUAL", feedback: "You expected any value to equal itself. 0 / 0 produces NaN, and the rule for numbers says NaN is not equal to anything, itself included. The text below walks the rule." },
    { id: "c", text: "false true false false", misconception: "EQ-STRINGS-BY-IDENTITY", feedback: "In Java, == on two String objects asks whether they are the same object, so a string built at run time can differ from a literal. JavaScript strings are primitives with no identity, so === compares their characters." },
    { id: "d", text: "false true true true", misconception: "VAL-EQUAL-BY-CONTENT", feedback: "You expected === to compare the arrays' contents. For objects, === asks only whether both sides are the same object (segment 7). [] and [] are two objects." }
  ]}
  explain="IsStrictlyEqual: different types are never equal; numbers use Number::equal, where NaN never matches and +0 equals -0; strings compare by characters; objects by identity."
/>
The spec names the algorithm IsStrictlyEqual. It has three steps:

1. If the two values have different types, return `false`.
2. If both are numbers, use the number rule, `Number::equal` (the spec writes number-only operations as `Number::name`).
3. Otherwise use `SameValueNonNumber`: `undefined` equals `undefined`, `null` equals `null`, bigints match when they are the same whole number, booleans match when both are true or both false, and strings match when they have the same length and the same 16-bit code units in the same places (for everyday text, the same characters). Everything else, which means objects and symbols, is "compared by identity".

That explains three answers. The two strings have the same characters. `[]` and `[]` are two objects. `0 === -0` is `true` because the number rule says `+0` and `-0` are equal. The first answer needs one more idea.

Some calculations have no numeric answer at all: `0 / 0`, `Number("abc")`, `Math.sqrt(-1)`. Numbers are floating point, like Java's `double`, so these do not throw. JavaScript returns one special Number value that means "not a number". It is called <Term id="nan">NaN</Term>. It usually spreads: most arithmetic with it gives it again (one exception: `NaN ** 0` is `1`). The number rule says: if either side is NaN, return `false`.

<Code runnable code={`console.log(0 / 0, Number("abc"), Math.sqrt(-1), 0 * Infinity); // → NaN NaN NaN NaN
console.log(NaN + 1, NaN === NaN); // → NaN false
console.log(Number.isNaN(NaN), Number.isNaN("abc"), isNaN("abc")); // → true false true`} />

So `x === x` is false when `x` is NaN, and NaN is the only value for which that happens.

You may ask: why would a value not be equal to itself? MDN says this rule is not JavaScript's invention; it comes from IEEE 754, the floating-point standard that JavaScript numbers follow. One way to see why it is reasonable (a way to think about it, not history): NaN can come from very different failed calculations, so calling two of them equal would claim something nobody knows. To test for it, use `Number.isNaN(x)`. The older global `isNaN` converts its argument first, so `isNaN("abc")` is `true`.

<Segment id="s13-same-value" goal="Object.is runs SameValue, which differs from === only for NaN and the two zeros; includes, Map and Set use SameValueZero">

## `Object.is` and the two zeros

Strict equality has two quirks with numbers: NaN is not equal to NaN, and `+0` equals `-0`. Sometimes you want a check with no exceptions, one that says "these are exactly the same value". The spec has one, called <Term id="same-value">SameValue</Term>, and `Object.is(a, b)` runs it. It is IsStrictlyEqual with a different number rule: NaN equals NaN, and `+0` does not equal `-0`.

You may ask: why does JavaScript have two zeros at all? Numbers follow IEEE 754, which has a positive and a negative zero. The sign can carry information: `1 / -0` is `-Infinity`, and `Math.round(-0.4)` gives `-0`, which still records that the value came from the negative side.

<Code runnable code={`console.log(Object.is(NaN, 0 / 0)); // → true
console.log(Object.is(0, -0)); // → false
console.log(1 / 0, 1 / -0); // → Infinity -Infinity
console.log([NaN].includes(NaN)); // → true
console.log([NaN].indexOf(NaN)); // → -1
console.log(new Set([0, -0, NaN, NaN]).size); // → 2`} />

A third comparison rule, SameValueZero, is SameValue except that `+0` and `-0` count as equal. `arr.includes(x)` (does the array contain `x`?), `Map` and `Set` use it. A Set holds unique values and a Map holds key-value pairs, like Java's HashSet and HashMap. So `includes` finds NaN, and the Set keeps one zero and one NaN. `arr.indexOf(x)` (where is `x`, or -1) uses `===`, so it never finds NaN.

Which one should you use? MDN: "Strict equality is almost always the correct comparison operation to use." `Object.is` matters when NaN or `-0` matters. React, the UI library, uses it to decide whether state changed (segment 20).

<Sidenote>Spec 20.1.2.15: Object.is returns "SameValue(value1, value2)". SameValue "differs from the IsStrictlyEqual Algorithm by treating all NaN values as equivalent and by differentiating +0 from -0". [SameValue](https://tc39.es/ecma262/#sec-samevalue), [MDN equality](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Equality_comparisons_and_sameness)</Sidenote>

</Segment>

<Segment id="s14-loose-equality" goal="== runs IsLooselyEqual, an ordered list of rules that either converts one side and compares again or decides directly, and uses === once the types match">

## `==` converts before it compares

JavaScript has a second equality operator, `==`. When the two sides have different types, it does not give up the way `===` does. It walks an ordered list of rules: most convert one side to another type and compare again, and a few decide the answer directly. This is called <Term id="loose-equality">loose equality</Term>, and the spec algorithm is IsLooselyEqual. A conversion that an operator does for you, without you asking, is usually called <Term id="coercion">coercion</Term>. That is a teaching name; the spec has no single operation by that name, only specific ones like ToNumber, which turns a value into a number. Predict these four.

<Predict

  explain="IsLooselyEqual converts one side at a time (a boolean to a number, a string to a number, an object to a primitive) until the types match, and treats null and undefined as equal only to each other."

IsLooselyEqual is a list of rules, checked in order. The spec writes most rules twice, once for each order of the two sides, so for the same two values `a == b` and `b == a` give the same result. Below, each pair is one rule, with the spec's step numbers in brackets.

1. Same type: return the result of IsStrictlyEqual (step 1).
2. One side `null` and the other `undefined`: return `true` (steps 2 and 3).
3. A browser-only rule for the old `document.all` object, kept for very old web pages; you can ignore it (step 4).
4. A number and a string: convert the string with ToNumber, then compare again (steps 5 and 6).
5. A bigint and a string: convert the string to a bigint (if it is not a valid bigint, return `false`), then compare again (steps 7 and 8).
6. A boolean on either side: convert it with ToNumber (`false` becomes `0`, `true` becomes `1`), then compare again (steps 9 and 10).
7. An object and a string, number, bigint or symbol: convert the object with ToPrimitive (next segment), then compare again (steps 11 and 12).
8. A bigint and a finite number: compare their mathematical values (step 13).
9. Nothing matched: return `false` (step 14).

Rules 4, 6, 7 and 8 at work:

<Code runnable code={`console.log(1n == 1, "1" == 1, true == 1, [2] == 2); // → true true true true`} />

ToNumber turns `null` into `0` when it is asked. But no rule above ever asks it about `null`. So `null == 0` reaches rule 9 and is false, while `null == undefined` stops at rule 2. `"" == 0` uses rule 4: the empty string becomes `0`. `"0" == false` uses rule 6 (`false` becomes `0`), then rule 4 (`"0"` becomes `0`), then `0 === 0`.

You may ask: isn't `x == false` a way to ask whether `x` is falsy? No. Truthiness, whether `if` treats a value as true, is a different conversion, ToBoolean, used by `if`, `while` and `!`. `==` never uses it. `"0"` is truthy, yet `"0" == false` is `true`.

MDN's advice is short: "In most cases, using loose equality is discouraged." The one common use is `x == null`. It is true when `x` is `null` (rule 1) or `undefined` (rule 2), and false for every other value, because no other rule matches and rule 9 returns false. (In browsers, rule 3 also makes it true for `document.all`.)

The spec algorithm is ToPrimitive. If the object has a `Symbol.toPrimitive` method, that method alone decides, and it must return a primitive or a `TypeError` is thrown. Otherwise ToPrimitive calls OrdinaryToPrimitive with a hint, a word that says what kind of primitive is wanted:

- hint "string": try `toString`, then `valueOf`;
- hint "number": try `valueOf`, then `toString`.

The first method that returns a primitive wins. If neither does, it throws a `TypeError`.

You may ask: why `valueOf` first for `==`? Because `==` gives no hint. A `Symbol.toPrimitive` method would receive the hint "default"; without one, the spec falls back to "number". So `price` became `100` in both comparisons: `price == 100` is true and `price == "Rs 100"` compares `100` with `"Rs 100"`, which is false. Sometimes you want a copy where every nested object is copied too, so that changing any object in the copy never changes an object in the original. `clone.p instanceof Point` is false. Built-in types it supports, such as Date, Map and Set, do come back as the same built-in type.

`clone.left === clone.right` is true. While it walks the input, `structuredClone` keeps a map from each object it has already copied to its copy. When it meets `shared` a second time, it reuses the copy. The same map is what lets it copy a cycle, an object that refers back to itself, without looping forever. `clone.left === shared` is false, because the copy is a new object.

It has limits. It throws a `DataCloneError` for functions and for symbol values. A getter, a property computed by a function, is read once and its value stored as a plain property; setters, symbol-keyed properties and class private fields are not copied.

The Date became a string, NaN became `null`, the key holding `undefined` vanished, the Set became an empty object, and the cycle threw.

## Misconceptions

Each line is a wrong model, the smallest code that breaks it, and the segment that shows why.

- **"`let b = a` copies the object."** `let a = { n: 1 }; let b = a; b.n = 2;` leaves `a.n` at 2. Only the reference is copied (s06).
- **"Reassigning a name changes the object it used to point to."** After `b = { n: 2 }`, `a.n` is still 1. Reassignment moves one arrow and changes no object (s08).
- **"`const` makes the object read-only."** `const s = {}; s.theme = "dark";` works. Only the binding is immutable; `Object.freeze` protects an object's properties, one level deep (s09).
- **"A parameter is another name for the caller's variable."** `user = { name: "Kabir" }` inside `rename` does not move `player`. The parameter starts with a copy of the reference (s10).
- **"Primitives live on the stack, objects on the heap, by rule."** The spec never mentions a heap; V8 keeps strings on its heap (s11).
- **"Every value equals itself."** `NaN === NaN` is false; use `Number.isNaN` (s12).
- **"`===` on strings checks identity, as in Java."** Strings have no identity, so two strings with the same code units are always `===` (s12).

<Code runnable code={`let a = { n: 1 }; let b = a; b.n = 2;
console.log(a.n); // → 2

const s = { theme: "light" }; s.theme = "dark";
console.log(s.theme); // → dark

console.log(o.list.length); // → 2`} />

- **"`===` compares objects by contents."** `[] === []` is false (s07, s12).
- **"`x == false` asks whether `x` is falsy."** `"0" == false` is true, though `"0"` is truthy. `==` turns the boolean into a number (s14).
- **"`null == 0` because `null` becomes 0."** No rule of IsLooselyEqual converts `null`, so the answer is false (s14).
- **"Spread copies everything."** Nested objects stay shared; a spread is a shallow copy (s16).
- **"`structuredClone` keeps classes and splits shared objects."** It drops custom class prototypes and keeps shared objects shared (s17).

## In the wild

**React.** When you call a `useState` setter, React compares the new value with the current one using `Object.is`. The React docs: "If the new value you provide is identical to the current state, as determined by an Object.is comparison, React will skip re-rendering the component and its children." So `obj.x = 10; setObj(obj);` does not re-render. The mutation already happened, but `setObj` got the same reference back, so `Object.is` says nothing changed and React skips the update. Now the state object and the screen disagree. The fix from the same page is a new object: `setObj({ ...obj, x: 10 })`. That copy is shallow, so for nested state you copy each level you change, as the next example shows. React treats state as read-only: replace it, do not mutate it.

**A chess board.** A shallow copy hides a second trap when state is nested. In a chess app, a board is often an array of rows.

<Code runnable code={`const board = [["", ""], ["", ""]];
const next = [...board];
next[0][1] = "K";
console.log(board[0][1]); // → K
console.log(next === board, next[0] === board[0]); // → false true`} />

`[...board]` made a new outer array, but every row is shared, so setting a square on `next` changed the old board too. React would see a new outer array and re-render, but your history of past positions would be silently wrong. Copy the row you change as well: `next[0] = [...board[0]]`, then set the square.

**Zod.** Many Node APIs validate input with Zod. Its docs say that if the input is valid, "Zod returns a strongly-typed deep clone of the input". For an object schema, the object you get back is a new object, not the one you passed in. Fields typed `z.any()` or `z.unknown()` are the exception: we checked with the Zod in this repository, and they pass the same reference straight through.

**Java.** Java's `a == b` on objects is JavaScript's `===`: identity. Java's `a.equals(b)` is a method each class can override to compare contents. JavaScript objects have no such built-in method, so code that needs to compare contents uses a library function or writes one, like the lab's `deepEqual`.
