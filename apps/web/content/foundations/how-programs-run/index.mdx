<Segment id="s02-program" goal="A program is instructions, and the CPU cannot read the text you write">

A computer does nothing on its own. It follows a list of instructions, and that list is a <Term id="program">program</Term>.

You write instructions as text, in a language like JavaScript, Java or C. Text written for people to read and change is called <Term id="source-code">source code</Term>.

One chip does the actual work. It carries out instructions one after another, very fast. That chip is the <Term id="cpu">CPU</Term>, the central processing unit, also called the processor.

You may think, "My computer runs my JavaScript, so the chip must understand JavaScript." It does not. The CPU cannot read the text `return a + b`. It understands only a small, fixed set of instructions, written as numbers. Something has to stand between your text and the chip, either translating the text or carrying it out. Most of this lesson is about that something.

<Code runnable code={`function add(a, b) {
  return a + b;
}
console.log(add(2, 3));
console.log(add.toString());`} />

The first line prints `5`. The second prints your function back, exactly as you typed it. So the software running this code still holds your function as text. That text is the source code, and it is never handed to the chip as it is. The next segment shows what the chip runs instead.

</Segment>

<Segment id="s03-machine-code" goal="The CPU runs only machine code: numbered instructions stored as bytes">

Computers store everything as bits. A bit is a 0 or a 1. Eight bits make a <Term id="byte">byte</Term>, and one byte can hold a whole number from 0 to 255.

A CPU runs instructions that are themselves numbers, stored as bytes. Each CPU family has its own list of instructions and its own number for each one. Instructions in this numeric form are <Term id="machine-code">machine code</Term>. Machine code is the only thing a CPU can run directly.

To get machine code from source code, you need a translator. A program that translates code into another form before the code runs is a <Term id="compiler">compiler</Term>. `gcc` is a compiler for C.

<Code code={`// add.c                          machine code from gcc 13.3 -O1, x86-64 Linux
int add(int a, int b) {           // 8d 04 37    lea eax,[rdi+rsi*1]
  return a + b;                   // c3          ret
}`} />

This is real output. The whole C function became four bytes, `8d 04 37 c3`. The first three bytes are one instruction, `lea`. It adds the two inputs and puts the sum where the caller looks for the answer. The inputs arrive in registers, which are tiny named storage slots inside the CPU, such as `rdi` and `rsi`. The last byte, `c3`, is the instruction `ret`, which means "go back to the code that called me".

Why can't one set of bytes run on every computer? Each CPU family has its own instruction set. An ARM chip, the kind in most phones and in Apple M-series laptops, uses different numbers, so `8d 04 37 c3` means nothing useful to it. A C program has to be compiled again for each CPU family.

A JavaScript file is text, and it stays text when you ship it. The same `.js` file runs on an x86 laptop and on an ARM phone. So each machine needs something that turns that text into work for its own CPU. Segments 7 to 11 show what that something is.

<Segment id="s04-memory" goal="Memory is one long row of bytes, each with a numbered address">

While code runs, the CPU needs a place to keep the instructions it is running and the data they work on. That place is <Term id="memory">memory</Term>, also called RAM. Picture it as one very long row of bytes.

Each byte in the row has a position number, starting at 0. That number is the byte's <Term id="address">address</Term>. To read or write a byte, the CPU gives its address. Addresses are usually written in hexadecimal (base 16), such as `7ffe3f1e4000`.

One byte stops at 255. A bigger number uses several bytes side by side.

JavaScript code never sees real addresses, so the Predict uses a model. A `Uint8Array` is a JavaScript object that behaves like a short row of bytes. Its indexes 0, 1, 2 and 3 play the role of addresses.

```text
address:   0      1      2      3      4      5   ...
         +------+------+------+------+------+------+
 bytes:  |  12  | 200  |   0  | 255  |  44  |   7  |  ...
         +------+------+------+------+------+------+
```

Is a `Uint8Array` real memory? Its bytes are stored in real memory, but its indexes are not real addresses. The software in between picks the real addresses and hides them.

</Segment>

<Segment id="s05-process" goal="The operating system runs each program as a process with its own private memory">

Many programs run on one computer at the same time: a browser, an editor, a Node server. One program is in charge of all of them. It starts them, gives each one turns on the CPU, and keeps them apart. That program is the <Term id="operating-system">operating system</Term> (OS), such as Linux, Windows or macOS.

A running program, as the operating system sees it, is a <Term id="process">process</Term>. Each process gets its own private range of memory addresses, called its address space. Code in one process cannot read or write another process's memory by accident.

On Linux, a process can read a map of its own memory from the file `/proc/self/maps`. Below, the same command ran twice, so two separate `node` processes printed part of their maps.

<Code code={`// node -e 'const maps = require("fs").readFileSync("/proc/self/maps", "utf8");
//   console.log(maps.split("\\n").filter((l) => /\\[(heap|stack)\\]/.test(l)).join("\\n"))'

// run 1
63fbdd2b8000-63fbdd520000 rw-p 00000000 00:00 0   [heap]
7fffa371a000-7fffa373c000 rw-p 00000000 00:00 0   [stack]

// run 2, the same command again
62a12068b000-62a1208f3000 rw-p 00000000 00:00 0   [heap]
7ffd5c40c000-7ffd5c42e000 rw-p 00000000 00:00 0   [stack]`} />

The address ranges differ. And even if two processes used the same address number, it would name a different byte in each, because each process has its own map.

<Sidenote>The Linux manual page for [fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html), the call that copies a process, says "The child process and the parent process run in separate memory spaces."</Sidenote>

Are two browser tabs two processes? The Predict asks the part of that question that matters for your code.

</Segment>

<Segment id="s06-thread" goal="A thread is one path of execution, and JavaScript runs your code on one thread at a time">

Inside a process, the CPU follows one instruction after another. One such path through the code is a <Term id="thread">thread</Term>. A process can run several threads at once, for example one on each CPU core.

<Sidenote>The Linux manual page [pthreads(7)](https://man7.org/linux/man-pages/man7/pthreads.7.html) says threads "share the same global memory ..., but each thread has its own stack". Segment 13 explains that stack.</Sidenote>

Your JavaScript is different. The specification gives each agent, its word for one running JavaScript world, one executing thread. MDN says an agent "is analogous to a thread". So while one of your functions runs, no other JavaScript in that page or Node program runs.

The Predict uses `setTimeout(fn, 0)`, which asks for `fn` to be called later, after at least 0 ms. Lesson 1.7 explains where `fn` waits.

"Run to completion" is the usual teaching name for this rule.</Sidenote>

In a browser, a long loop means the page cannot react to clicks or scrolling (MDN). In Node, every other request waits.

You may ask, "My laptop has many cores, so why does one loop block the timer?" More cores help only when more than one thread has work to do, and your JavaScript has one. In Java, the OS can switch between threads at almost any instruction, so two Java threads really can interleave.

</Segment>

<Segment id="s07-interpreter" goal="A compiler translates ahead of time; an interpreter carries out code itself; bytecode sits between">

There are two ways to get source code running. The first is to compile it. A compiler translates all of it to machine code ahead of time, and then the CPU runs that machine code, as with gcc in segment 3. The second is to hand your code to a program that reads it and carries out each step itself. That program is an <Term id="interpreter">interpreter</Term>. The interpreter is itself machine code. The CPU runs the interpreter, and the interpreter runs your code.

<Code code={`// compile ahead of time:  add.c ---gcc---> machine code ---> the CPU runs it
// interpret:              add.sh -------------------------> bash, itself machine code, reads it and does each step
// bytecode (Java):        Add.java --javac--> bytecode (.class) ---> the JVM interprets it,
//                                                                     and compiles hot methods to machine code`} />

Each way has a cost. Compiling takes time before the first run, but the result runs fast. Interpreting starts at once, but every step costs extra work, because the interpreter has to look at each instruction and decide what to do.

There is a middle path. A compiler can translate source code into a compact list of simple instructions designed for an interpreter, not for a CPU. That form is <Term id="bytecode">bytecode</Term>. It is easier and faster to interpret than raw text.

Java, which you use at work, does exactly this. `javac` compiles `.java` files into `.class` files full of bytecode, and the JVM runs that bytecode.

<Sidenote>The [java command docs](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html), option `-Xmixed`: "Executes all bytecode by the interpreter except for hot methods, which are compiled to native code. On by default." Native code means machine code. Hot means run often.</Sidenote>

So is Java compiled or interpreted? Both, at different moments. The next segments show that JavaScript is the same.

<ExplainBack
  id="e-compile"
  prompt="In one sentence, what does a compiler produce, and what does an interpreter do instead?"
  rubric={["A compiler produces new code (machine code or bytecode) before the code runs", "An interpreter produces no machine code for your program; it carries out each step itself while reading", "The interpreter is itself machine code that the CPU runs"]}
/>

A compiler produces new code and then stops. An interpreter produces no machine code for your program. It does the work itself while it reads. Java uses both. JavaScript does too, but there is no separate compile step that you run yourself.

</Segment>

<Segment id="s08-engine-host" goal="The engine implements the language; the runtime (host) adds the outside world">

Running JavaScript takes two pieces of software working together. The first knows the language itself, with its numbers, strings, objects and functions, and built-ins such as `Math`, `Array` and `JSON`. It reads your source code, parses it and runs it. This is the <Term id="engine">engine</Term>, or JavaScript engine. V8 is the engine in Chrome and in Node. Firefox uses SpiderMonkey, and Safari uses JavaScriptCore.

The second piece is the program around the engine. It gives JavaScript a way to reach the outside world. This is the <Term id="runtime">runtime</Term>, which the specification calls the host. A browser adds the page (`document`), timers and `fetch`. Node adds files, network sockets, information about its own process, and its own timers.

<Sidenote>MDN, [Execution model](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model): "JavaScript execution requires the cooperation of two pieces of software: the JavaScript engine and the host environment." The specification, [section 4.1](https://tc39.es/ecma262/multipage/overview.html#sec-web-scripting): "A web browser provides an ECMAScript host environment ... A web server provides a different host environment."</Sidenote>

Isn't `console.log` part of JavaScript? Commit to an answer before you read on.

</Segment>

<Segment id="s09-parse-first" goal="The engine parses the whole script before running any of it, so early errors stop everything">

Now you can explain the hook from segment 1. Before it runs anything, the engine parses the whole file. Parsing means reading all of the text and building a tree that shows how the code fits together, for example which parts are functions and which statements sit inside which blocks. Running the code is a separate step that starts only after parsing succeeds.

While parsing, the engine also looks for early errors. These are mistakes it can find without running anything. Declaring the same `let` name twice in one scope is one of them. That is why the hook printed nothing, not even `one`. The older keyword `var` allows a repeated declaration, so the same file with `var` runs to the end.

<Code runnable code={`console.log("one"); // → one
console.log("two"); // → two
var total = 1;
var total = 2;`} />

<Sidenote>The specification, [section 17](https://tc39.es/ecma262/multipage/error-handling-and-language-extensions.html#sec-error-handling-and-language-extensions): "An early error is an error that can be detected and reported prior to the evaluation of any construct in the Script containing the error. ... An implementation must report early errors in a Script as part of parsing that Script in ParseScript." [ParseScript](https://tc39.es/ecma262/multipage/ecmascript-language-scripts-and-modules.html#sec-parse-script) is the spec's name for the parse step. Running is a later step, ScriptEvaluation.</Sidenote>

Now change one thing. Move the repeated `let` inside a function that is never called.

V8 adds a detail of its own here. It does not fully compile a function until the function is called. To save time, it preparses the function body instead, which is a quicker pass that still checks the syntax. This is how V8 works, not a rule of the language.

<Sidenote>V8 blog, [lazy parsing and the preparser](https://v8.dev/blog/preparser) (2019): "The preparser verifies that the functions it skips are syntactically valid."</Sidenote>

Why check code that never runs? The specification requires it, and the result is one clear rule. A script either has no early errors and starts, or it does not start at all. You never get a half-run file because of an early error near the bottom.

Not every mistake is an early error, though. The specification says an implementation "shall not treat other kinds of errors as early errors". Reading a variable that does not exist is only noticed when that line runs. The code below never calls the function, so it runs to the end.

<Segment id="s10-bytecode" goal="V8 turns each function into bytecode, usually the first time it is called">

V8 does not run the parsed tree directly. It first turns each function into bytecode, and an interpreter called Ignition runs that bytecode. Ignition, and everything in the next three segments, is how V8 works, not a rule of JavaScript.

<Sidenote>V8 blog, [Maglev](https://v8.dev/blog/maglev) (2023): "All JavaScript code is first compiled to ignition bytecode, and executed by interpreting it."</Sidenote>

You can see this bytecode yourself. Node prints it with the flag `--print-bytecode`. Below is real output from Node v26 (V8 14.6) for `function add(a, b) { return a + b; }`. The whole function is 6 bytes long and has three instructions.

- `Ldar a1` loads the second parameter, `b`, into the accumulator. The accumulator is one special slot that most Ignition instructions read from and write to. It is a V8 word, not a JavaScript term.
- `Add a0, FBV[0]` adds the first parameter, `a`, to the accumulator. `FBV[0]` names a feedback slot, a small record where V8 notes what kinds of values it saw at this spot, such as "both were small integers". Segment 11 shows why that matters.
- `Return` returns whatever is in the accumulator.

Compare this with segment 3. The CPU cannot run `Ldar` or `Add`. Ignition is machine code, and it reads these bytes and does the work.

```text
$ node --print-bytecode --print-bytecode-filter=add add.js
[generated bytecode for function: add (...)]
Bytecode length: 6
Parameter count 3
Register count 0
Frame size 0
   0 : 0b 04       Ldar a1
   2 : 40 03 00    Add a0, FBV[0]
   5 : b7          Return
```

Why not make all the bytecode at once? Many functions in a real web page never run. Making their bytecode would waste startup time and memory.

</Segment>

<Segment id="s11-jit" goal="Hot functions get compiled to machine code while the program runs, based on what V8 has seen">

An interpreter is flexible, but it pays a cost on every instruction. The V8 team wrote that "interpreters have inherent overheads that we can't get rid of" ([Sparkplug](https://v8.dev/blog/sparkplug), 2021).

So V8 watches your code while it runs. A function that runs often is called hot, and V8 compiles hot functions to machine code that the CPU runs directly. Compiling to machine code while the program is already running is called <Term id="jit">JIT</Term> compilation, short for just-in-time.

V8 has four tiers today.

- Ignition interprets bytecode.
- Sparkplug (2021) turns bytecode into machine code "almost instantaneously", without optimizing it.
- Maglev (2023) is a fast optimizing compiler that "sits between our existing Sparkplug and TurboFan compilers".
- TurboFan is the top tier, "focused on peak performance". In 2025 the V8 team described moving TurboFan's back end to a new internal design called Turboshaft. TurboFan is still the name of the top tier.

A JIT compiles code. It does not store results. Every call still runs and computes its answer. Saving results is a different technique, memoization, which you write yourself.

You may ask, "If machine code is faster, why not compile everything at the start?" Compiling costs time, and the optimizing compilers need feedback that only exists after the code has run for a while. Most code never runs often enough to repay that cost.

One practical result is warm-up. When you time code, the first runs are often slower than later ones, so do not trust a single measurement.

</Segment>

<Segment id="s13-call-stack" goal="Each call that has not finished is a frame on the call stack; calling pushes, returning pops">

Back to the one thread that runs your code. When one function calls another, the caller pauses in the middle of a line. When the inner function returns, the caller has to continue from exactly that spot, with its own variables still in place. So the engine keeps a record for every call that has started but not finished. The record says which function it is, where it paused, and what its variables hold. That record is a <Term id="stack-frame">stack frame</Term>.

The frames form a list. A new call goes on top, and only the top frame runs. When a call returns, its frame is removed from the top. Last in, first out, like a stack of plates. This list is the <Term id="call-stack">call stack</Term>.

<Sidenote>The specification calls a frame an "execution context" and the list the "execution context stack" ([section 9.4](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-execution-contexts)): "The running execution context is always the top element of this stack." Lesson 1.2 uses those names.</Sidenote>

Before you step, learn the two parts of the picture. The left column is the call stack, newest frame on top, with the script's own frame at the bottom. The right side shows each call's variables in a box of its own. Lesson 1.2 gives those boxes their proper name. The visualizer stops once and asks what changes next.

<Viz example="nested-calls" view="scope" pauseAt={[4]} title="Call stack: nested calls" />

`square` was called twice, and each call got its own frame, one after the other. The second frame started fresh with `n = 4`. Nothing was left over from the first call.

Only the top frame was ever running. The frames below it were paused, each waiting for a value to come back.

Where does `sumOfSquares` wait while `square` runs? In its own frame. The frame records the exact spot, the middle of `const x = square(a)`, and the values of `a` and `b`. That record is what lets one thread go down into calls and come back up.

</Segment>

<Segment id="s14-recursion" goal="A recursive function gets a separate frame for every call, each with its own variables">

A function that calls itself is recursive. The call stack does not care that it is the same function. Every call gets a new frame.

Before you step, decide. Will the three calls of `factorial` share one `n`, or will each call have its own? Watch the right side as you step.

<Viz example="factorial" view="scope" pauseAt={[8]} title="Call stack: recursion" />

Three `factorial` frames were on the stack at the same time, holding `n = 3`, `n = 2` and `n = 1`. Each frame had its own `n`.

The deepest call finished first. Then each frame below it received an answer and finished in turn: 1, then 2 × 1 = 2, then 3 × 2 = 6. The condition that stops the recursion, here `n === 1`, is called the base case.

Every frame takes up space until its call returns. That is the cost of recursion. The next segment shows what happens when the calls never stop.

</Segment>

You may ask, "Why is the limit so small when my laptop has gigabytes of memory?" Each thread's stack is one fixed-size block, set by the engine or the OS, and frames sit side by side inside it. The specification sets no limit and names no error for this. Who removes objects from the heap? Not you. In C you free memory yourself with `free()`. The engine finds objects that nothing can reach any more and reuses their memory. This work is called <Term id="garbage-collection">garbage collection</Term>. Lesson 1.9 shows how it decides.

You may ask, "So numbers live on the stack and objects on the heap?" You will hear that rule of thumb often, but it is not a rule of JavaScript. **Express and DevSecret.** An Express server runs every request handler on one JavaScript thread. A handler that does heavy CPU work synchronously blocks every other request until it finishes. The event loop is Node's name for the work that thread does, and lesson 1.7 covers it. Suppose DevSecret derives an encryption key from a password, as in the code above. `crypto.pbkdf2Sync` does that work on the main thread and blocks it. The callback version, `crypto.pbkdf2`, runs the work on Node's pool of helper threads, which the same page lists among its Worker Pool APIs.
