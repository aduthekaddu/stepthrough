<Segment id="s02-program" goal="A program is instructions, and the CPU cannot read the text you write">

<Figure diagram="text-vs-chip" title="Your text and the chip">
  <Step>A <Term id="program">program</Term> is a list of instructions. You write it as text that people can read and change, called <Term id="source-code">source code</Term>. The chip that carries out instructions is the <Term id="cpu">CPU</Term>.</Step>
  <Step>The CPU cannot read the text `return a + b`. It runs only a small, fixed set of instructions, written as numbers.</Step>
  <Step>So something must stand between your text and the chip. It either translates the text or carries it out. Most of this lesson is about that something.</Step>
</Figure>

Run it. The second line prints your function back, exactly as you typed it. The software running JavaScript still holds it as text.

<Code runnable code={`function add(a, b) {
  return a + b;
}
console.log(add(2, 3));
console.log(add.toString());`} />

</Segment>

<Segment id="s03-machine-code" goal="The CPU runs only machine code: numbered instructions stored as bytes">

<Figure diagram="machine-code" title="From C to machine code">
  <Step>Computers store everything as bits, each a 0 or a 1. Eight bits make a <Term id="byte">byte</Term>. One byte has 256 patterns, read as the numbers 0 to 255. This byte is `8d`, or 141.</Step>
  <Step>A <Term id="compiler">compiler</Term> translates code into other code. gcc does it ahead of time, turning this C function into four bytes. Instructions stored as numbers are <Term id="machine-code">machine code</Term>, the only thing a CPU runs directly.</Step>
  <Step>The first three bytes are one instruction, `lea`, used here to add `a` and `b`. The last byte, `c3`, is `ret`: go back to the code that called this one.</Step>
  <Step>Each CPU family numbers its instructions its own way. An ARM chip, the kind in most phones, cannot use these x86-64 bytes. A C program is compiled again for each family.</Step>
</Figure>

<Deeper title="The real compiler output">

This is gcc 13.3 on x86-64 Linux, with `-O1 -fcf-protection=none`. Without that last flag, Ubuntu's gcc adds a 4-byte security instruction in front.

<Code code={`// add.c                          gcc 13.3 -O1 -fcf-protection=none
int add(int a, int b) {           // 8d 04 37    lea eax,[rdi+rsi*1]
  return a + b;                   // c3          ret
}`} />

`lea` was designed for a different job, but compilers use it to add two numbers in one step, and the sum lands where the caller looks for the answer. The inputs arrive in registers, tiny named storage slots inside the CPU, such as `rdi` and `rsi`. Java's `byte` type reads the same 256 patterns as -128 to 127.

</Deeper>

</Segment>

<Segment id="s04-memory" goal="Memory is one long row of bytes, each with a numbered address">

<Figure diagram="memory-bytes" title="Memory is a row of bytes">
  <Step>While code runs, the CPU keeps its instructions and data in <Term id="memory">memory</Term>, also called RAM: one long row of bytes. Each byte's position number, from 0 up, is its <Term id="address">address</Term>.</Step>
  <Step>To read or write a byte, the CPU gives its address. Real addresses are large numbers, usually written in hexadecimal (base 16), such as `7ffe3f1e4000`.</Step>
  <Step>One byte stops at 255, so a bigger number takes several bytes side by side. 1000 is 3 × 256 + 232. This x86-64 machine stores it as 232, then 3.</Step>
  <Step>JavaScript never shows you real addresses. A `Uint8Array` behaves like a short row of bytes, and its indexes 0 to 3 play the role of addresses.</Step>
</Figure>

<Deeper title="The rule in the specification">

The specification calls this conversion [ToUint8](https://tc39.es/ecma262/multipage/abstract-operations.html#sec-touint8). It turns any number into one of the 256 values from 0 to 255.

Is a `Uint8Array` real memory? Its bytes sit in real memory, but its indexes are not real addresses. Software you meet in segments 5 and 8 picks the real addresses and hides them.

</Deeper>

</Segment>

<Figure diagram="process-memory" title="Each process has its own memory">
  <Step>The <Term id="operating-system">operating system</Term> (OS) starts programs, gives each a turn on the CPU, and keeps them apart. A running program, as the OS sees it, is a <Term id="process">process</Term>. Here `node` ran twice: two processes.</Step>

Your code can rely only on the first rule. Tabs do not share variables.

<Segment id="s06-thread" goal="A thread is one path of execution, and JavaScript runs your code on one thread at a time">

<Figure diagram="threads" title="Threads in a process">
  <Step>A <Term id="thread">thread</Term> is one path through a process's code, one instruction after another. Threads share the process's memory, but each has its own stack.</Step>
  <Step>A process can run several threads at once. Here two cores run threads 1 and 2 at the same moment.</Step>
  <Step>Your JavaScript gets one thread. A worker you start gets another, with its own memory.</Step>
</Figure>

<Deeper title="Run to completion, and many cores">

The Linux manual page [pthreads(7)](https://man7.org/linux/man-pages/man7/pthreads.7.html) says threads "share the same global memory ..., but each thread has its own stack". Segment 13 explains that stack.

The specification calls one running JavaScript world an agent and gives each agent one executing thread, and MDN says an agent "is analogous to a thread". A worker you start is another agent, with its own thread and memory. A process's threads can run at the same moment, for example one on each CPU core. So while one of your functions runs, no other JavaScript on that thread runs. The specification, section [Jobs](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-jobs): "Once evaluation of a Job starts, it must run to completion before evaluation of any other Job starts in an agent." "Run to completion" is the usual teaching name for this rule.

Lesson 1.7 shows where a waiting callback waits. In a browser, a long loop means the page cannot react to clicks or scrolling (MDN). In Node, every other request waits.

"My laptop has many cores, so why does one loop block the timer?" More cores help only when more than one thread has work to do, and your JavaScript has one. In Java, the OS can switch between threads at almost any instruction, so two Java threads really can interleave.

</Deeper>

</Segment>

<Segment id="s07-interpreter" goal="A compiler translates code, gcc ahead of time; an interpreter carries out code itself; bytecode sits between">

<Figure diagram="compile-vs-interpret" title="Compile, interpret, or both">
  <Step>One way to run source code is to compile it ahead of time. gcc turns `add.c` into machine code before the program starts. That takes time up front, but the result runs fast.</Step>
  <Step>The other way: an <Term id="interpreter">interpreter</Term> reads your code and carries out each step itself. bash, itself machine code, runs `add.sh` this way. It starts at once, but every step costs extra work.</Step>
  <Step>Between the two sits <Term id="bytecode">bytecode</Term>: a compact list of simple instructions made for an interpreter, not for a CPU. `javac` compiles `Add.java` to bytecode, and the JVM's interpreter runs it.</Step>
  <Step>The JVM also compiles hot methods, the ones that run often, to machine code. So is Java compiled or interpreted? Both, at different moments. JavaScript is the same.</Step>
</Figure>

  id="e-compile"
  prompt="In one sentence, what does a compiler produce, and what does an interpreter do instead?"
  rubric={["A compiler produces new code (machine code or bytecode), ahead of time like gcc or while the program runs", "An interpreter produces no machine code for your program; it carries out each step itself while reading", "The interpreter is itself machine code that the CPU runs"]}

<Deeper title="Interpreter costs, and Java's docs">

An interpreter has to look at each instruction and decide what to do, every time it runs it. The interpreter is itself machine code. The CPU runs the interpreter, and the interpreter runs your code. Bytecode is easier and faster to interpret than raw text.

The [java command docs](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html), option `-Xmixed`: "Executes all bytecode by the interpreter except for hot methods, which are compiled to native code. On by default." Native code means machine code. Hot means run often.

A compiler produces new code. It can do that before the program runs or, as segment 11 shows, while it runs. An interpreter produces no machine code for your program. It does the work itself while it reads. JavaScript uses both too, but there is no separate compile step that you run yourself.

</Deeper>

</Segment>

<Segment id="s08-engine-host" goal="The engine implements the language; the runtime (host) adds the outside world">

<Figure diagram="engine-runtime" title="Engine and runtime" gate="p-host">
  <Step>Running JavaScript takes two pieces of software. The <Term id="engine">engine</Term> knows the language and its built-ins, such as `Math` and `JSON`. It parses and runs your code. V8 is the engine in Chrome and in Node.</Step>
  <Step>The second is the program around the engine: the <Term id="runtime">runtime</Term>, which the spec calls the host. It lets JavaScript reach the outside world. A browser adds the page (`document`), timers, `fetch` and `console`.</Step>
  <Step>Node wraps the same V8 in a different runtime. It adds files, network sockets, its own process and its own timers. It has no page, so it has no `document`.</Step>
</Figure>

<Deeper title="Other engines, and console">

Firefox uses the SpiderMonkey engine, and Safari uses JavaScriptCore. MDN, [Execution model](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model): "JavaScript execution requires the cooperation of two pieces of software: the JavaScript engine and the host environment." The specification, [section 4.1](https://tc39.es/ecma262/multipage/overview.html#sec-web-scripting): "A web browser provides an ECMAScript host environment ... A web server provides a different host environment."

`Math` comes from the engine, so every JavaScript environment has it. `document` comes from the browser, so Node does not have it. `setTimeout` comes from the runtime too, and browsers and Node each supply their own version.

`console` is not in ECMAScript, the official JavaScript standard, at all. A separate document, the [WHATWG Console Standard](https://console.spec.whatwg.org/), defines it. Browsers and Node both provide one, and other runtimes may differ. The specification, [section 17](https://tc39.es/ecma262/multipage/error-handling-and-language-extensions.html#sec-error-handling-and-language-extensions): "a host or implementation may provide additional types, values, objects, properties, and functions beyond those described in this specification."

<Deeper title="The spec's rule, and V8's preparser">

Parsing means reading all of the text and working out how the code fits together, for example which parts are functions and which statements sit inside which blocks. Engines usually build a tree from it. How much detail they build is their choice.

The specification, [section 17](https://tc39.es/ecma262/multipage/error-handling-and-language-extensions.html#sec-error-handling-and-language-extensions): "An early error is an error that can be detected and reported prior to the evaluation of any construct in the Script containing the error. ... An implementation must report early errors in a Script as part of parsing that Script in ParseScript." [ParseScript](https://tc39.es/ecma262/multipage/ecmascript-language-scripts-and-modules.html#sec-parse-script) is the spec's name for the parse step. Running is a later step, ScriptEvaluation. The same section says an implementation "shall not treat other kinds of errors as early errors".

With `var`, the file from segment 1 runs to the end:

<Code runnable code={`console.log("one"); // → one
console.log("two"); // → two
var total = 1;
var total = 2;`} />

V8 adds a detail of its own. Many functions are not fully compiled until they are called. To save time, V8 preparses such a function's body instead, a quicker pass that still checks the syntax, and parses and compiles it fully on its first call. Some functions, such as one wrapped in parentheses, are compiled right away (segment 10). This is how V8 works, not a rule of the language. V8 blog, [lazy parsing and the preparser](https://v8.dev/blog/preparser) (2019): "The preparser verifies that the functions it skips are syntactically valid."

Why check code that never runs? The specification requires it, and the result is one clear rule. A script either has no early errors and starts, or it does not start at all. You never get a half-run file because of an early error near the bottom.

</Deeper>

</Segment>

<Segment id="s10-bytecode" goal="V8 turns each function into bytecode, usually the first time it is called">

<Figure diagram="ignition-bytecode" title="Ignition runs add(2, 3)">
  <Step>V8 turns each function into bytecode, and its interpreter, Ignition, runs it. These are the real 6 bytes for `add`: three instructions. Slots `a0` and `a1` hold the arguments, 2 and 3.</Step>
  <Step>`Ldar a1` loads `b`, which is 3, into the accumulator. The accumulator is one special slot that most Ignition instructions read from and write to.</Step>
  <Step>`Add a0, FBV[0]` adds `a` to it, so the accumulator now holds 5. `FBV[0]` is a feedback slot, where V8 notes what kinds of values it saw: here, small integers.</Step>
  <Step>`Return` hands back the 5 in the accumulator. The CPU never runs `Ldar` or `Add`. It runs Ignition, which is machine code, and Ignition does the work.</Step>
</Figure>

Bytecode and Ignition are how V8 works, not rules of JavaScript.

// [generated bytecode for function: add (...)]

Making bytecode only when a function is first needed is called lazy compilation. It is a V8 choice, and V8 bends it with its own rules. For example, it compiles a function wrapped in parentheses right away, because such functions are usually called at once. The specification only requires the parse and the early-error check from segment 9. It says nothing about bytecode.

Why not make all the bytecode at once? Many functions in a real web page never run. Making their bytecode would waste startup time and memory.

</Deeper>

<Deeper title="The tiers in V8's words">

The V8 team wrote that "interpreters have inherent overheads that we can't get rid of" ([Sparkplug](https://v8.dev/blog/sparkplug), 2021).

- Ignition interprets bytecode.
- Sparkplug (2021) turns bytecode into machine code "almost instantaneously", without optimizing it.
- Maglev (2023) is a fast optimizing compiler that "sits between our existing Sparkplug and TurboFan compilers" ([Maglev](https://v8.dev/blog/maglev)).
- TurboFan is the top tier, "focused on peak performance". In 2025 the V8 team described moving TurboFan's back end to a new internal design called Turboshaft. TurboFan is still the name of the top tier.

A function does not have to climb every rung. In the run in segment 12, `add` went from Ignition straight to Maglev. Tiers, thresholds and timing change between V8 versions, and the V8 posts cited here give no fixed "after N calls" number.

A JIT compiles code. It does not keep a table of past results. The optimizer may skip work whose result it can already prove, but everything your code does that you can observe, such as logging or changing a variable, still happens on every call. Saving results by arguments is a different technique, memoization, which you write yourself.

"If machine code is faster, why not compile everything at the start?" Compiling costs time, and the optimizing compilers need feedback that only exists after the code has run for a while. Most code never runs often enough to repay that cost. So when you time code, expect the first runs to be slower (warm-up).

</Deeper>

"During execution V8 tracks how the program behaves, including tracking object shapes and types" ([Maglev](https://v8.dev/blog/maglev)). The feedback slots from segment 10 hold this record. The optimizing compilers use it to make "often speculative" machine code, which is code that assumes the future will look like the past.

In V8's words, a deoptimization "tiers-down and continues the function's execution in the interpreter" ([Sparkplug](https://v8.dev/blog/sparkplug)). V8 rebuilds the interpreter's state at the exact point of the failed check, so work the function already did is not done twice.

Does JavaScript use only one thread, then? Your JavaScript does. But `ConcurrencyMode::kConcurrent` in the trace means V8 compiled `add` on a helper thread. V8 also uses helper threads to clean up unused memory (segment 16), and Node runs some slow work, such as file reads and `crypto.pbkdf2`, on a pool of helper threads. These helper threads never run your JavaScript functions. Only workers, which you start yourself, run JavaScript on other threads.

<Segment id="s13-call-stack" goal="Each call that has not finished is a frame on the call stack; calling pushes, returning pops">

<Viz example="nested-calls" view="scope" pauseAt={[4]} title="Call stack: nested calls" />

Each call that has started but not finished keeps a record: which function it is, where it paused, and what its variables hold. That record is a <Term id="stack-frame">stack frame</Term>. A call pushes a new frame on top, only the top frame runs, and a return removes it. Last in, first out. That list, the left column above, is the <Term id="call-stack">call stack</Term>.

<Deeper title="Paused callers, and the spec's names">

A caller pauses in the middle of a line, and its frame keeps that spot and its variables. So `sumOfSquares` waits in its own frame while `square` runs, paused inside `const x = square(a)` with `a` and `b` still set. That is what lets one thread go down into calls and come back up. The right side of the picture shows each call's variables in a box of its own. Lesson 1.2 gives those boxes their proper name.

A frame also leaves when an error is thrown out of its call. Generators and async functions, in later lessons, can pause a frame and resume it.

The specification calls a frame an "execution context" and the list the "execution context stack" ([section 9.4](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-execution-contexts)): "The running execution context is always the top element of this stack." This is an abstract model. Engines build real frames, and an optimizer may even merge a small function into its caller (inlining).

</Deeper>

</Segment>

<Segment id="s14-recursion" goal="A recursive function gets a separate frame for every call, each with its own variables">

<Viz example="factorial" view="scope" pauseAt={[8]} title="Call stack: recursion" />

A function that calls itself is recursive, and each call gets its own frame. Three `factorial` frames held `n` = 3, 2 and 1 at once. The deepest returned first, then 2 × 1 = 2, then 3 × 2 = 6. `n === 1`, which stops the recursion, is the base case. Every frame takes space until its call returns.

</Segment>

<Deeper title="Count the frames, and other engines">

A `while (true) {}` loop pushes no frames, so it can run forever without overflowing.

"Why is the limit so small when my laptop has gigabytes of memory?" A thread's stack is one fixed-size block that the OS sets up, and frames sit side by side inside it. V8 also sets its own, smaller limit on how much of that stack JavaScript may use: 984 KB by default (`node --v8-options` describes `--stack-size=984` as the "default size of stack region v8 is allowed to use"). Run the code below to count how many frames fit. On Node v26, it counted 12,517 frames on the machine used for this lesson. Bigger frames mean fewer calls. Java works the same way. `-Xss` sets the stack size per thread (1024 KB by default on Linux x64), and running out throws `StackOverflowError`.

<Code runnable code={`let depth = 0;

  depth++;
  dive();
}
try {
  dive();
} catch (e) {
  console.log("frames before the overflow:", depth);

The specification sets no limit and names no error for this, so the overflow itself is engine behaviour. MDN lists `RangeError` in Chrome and Safari, but `InternalError: too much recursion` in Firefox ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Errors/Too_much_recursion)). Those are engine choices. The fix is in your code. Give the recursion a base case, or turn very deep recursion into a loop.

The specification does describe one way around this, called proper tail calls. In strict mode, when a function's last act is to return another call, the spec discards the current frame before that call ([PrepareForTailCall](https://tc39.es/ecma262/multipage/ecmascript-language-functions-and-classes.html#sec-preparefortailcall)). V8 does not do this. In Node v26, a strict-mode function that ends with `return count(n - 1)` still overflows at a depth of 100,000.

<Deeper title="The heap, and who frees memory">

Objects live outside frames, in a region of memory whose data is not tied to one call: the <Term id="heap">heap</Term>. An object stays while something can still reach it. Once nothing can, the engine may free its memory later. That is <Term id="garbage-collection">garbage collection</Term>.

A frame's local variables can no longer be reached through that call once it returns. (Lesson 1.3 shows the one way they can survive.) A variable holds a way to reach an object, not the object itself (lesson 1.1 shows this). MDN calls the heap "just a name to denote a large (mostly unstructured) region of memory".

In C you would call `free()`. JavaScript does it for you. MDN says JavaScript "automatically allocates memory when objects are created and frees it when they are not used anymore". An object that nothing can reach becomes eligible to be freed, and the engine may reuse its memory later. An object you forgot but can still reach, say in a cache that only grows, is never freed. Lesson 1.9 covers such leaks.

"So numbers live on the stack and objects on the heap?" It is a common rule of thumb, not a rule of JavaScript. The specification never mentions a stack region or a heap. Where values are stored is the engine's choice. V8 can even skip creating an object that never leaves its function.

**A chess server and React.** In a chess server like this one, one Node process holds every WebSocket connection, and it handles all their messages on its one JavaScript thread. React runs your components on the main thread, so a slow synchronous render freezes clicks and scrolling. MDN says that while a long job runs, the page "is unable to process user interactions like click or scroll".

**Java servers.** Java runs on the JVM. Java servlet containers usually handle requests on a pool of threads, so one slow request does not hold up the others in the same way. Apart from that difference, the JVM uses the same machinery as V8. It has bytecode, an interpreter, a JIT for hot methods (`-Xmixed`), a fixed-size stack per thread (`-Xss`, `StackOverflowError`), and a garbage-collected heap with a maximum size (`-Xmx`). Node passes similar flags to V8, such as `--stack-size` and `--max-old-space-size`. The second one limits only V8's "old space", the part of the heap for long-lived objects, so it is close to `-Xmx` but not the same.
